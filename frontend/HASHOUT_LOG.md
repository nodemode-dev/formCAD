## H26, v0.19.0 the home is a port of formdeck's home, not an approximation of it (ui/home.ts, styles/home.css, ui/shell-part1.ts)

The home written in 0.17.0 took formdeck's layout by eye. On the owner's Mac it did not look like formdeck: a 320 px side panel against formdeck's 232, flat boxes, four fixed columns of wide tiles, section links pushed to the far right, a dashed empty box, and the status bar still showing under it. This entry is the port, measured against formdeck running beside it.

Side panel. 232 px by default; a 6 px strip on its edge resizes it between 180 and 420 px and collapses it below 120; a 14 by 56 px tab on the edge hides and shows it, and when it is hidden the tab sits alone on the window's left edge and the content re-centres, as in formdeck. Width and hidden state are stored (`formCAD.homeNav`, `formCAD.homeNavHidden`, under the prefix Reset Settings clears) and applied before the home is mounted. Items, the active item, count badges, section titles, the separator and the pinned foot carry formdeck's measurements and states on formCAD's tokens.

Content. Padding 32/40/56; the hero has formdeck's dashed line, faint accent glow, raised icon tile, mono format tags and 36 px actions; "See all" and the notes sit beside each section title. One card class, `cv-card`, for demos, templates, recent files, projects and outputs, in grids that fill the width from 208 px columns. Templates have category chips (Drawing, Model, Graph) and a search box, on Start and on the Templates page, kept in step; filtering hides cards in place. Recent holds its place with a skeleton card that becomes a same-size "No drawings yet" card, so nothing jumps. The narrow tab row appears below 720 px (it was 1100).

Window. While the home is open, `body.cv-home-open` hides the status bar and the home reaches the bottom of the window. The bar keeps its box and is only made invisible, so the editor underneath does not move when the home opens or closes. The title bar stays: it carries the window controls and the drag area.

Left out because formCAD has no data for them: formdeck's trash, the per-card menu (pin, hide, delete with undo), its agents group, its template preview. formdeck's two head buttons touch; formCAD keeps its 8 px gap.

formdeck has no minirail: no rail class anywhere but its preferences dialog. The nearest thing on its home is the hide and show tab, which is ported.

Measured with the processor slowed 4 times: layout shift 0 on a cold load, a hard reload, switching between the five sections, and opening the home over a drawing and going back; 0.00003 on opening a demo, from the editor; no node added or removed when the panel collapses. Collapsing or expanding the panel moves the content (0.306 when the click comes from a script), which is the re-centring formdeck does and the direct answer to the click. Looked at in Studio Dark, AMOLED Black and Light, at 1440, 1920, 900 and 700 px wide.

## R24, v0.18.0 the display pull follows the active document (canvas/renderer.ts)

Found while chasing the open defect below; it is a real fault of its own and not that defect's cause. `Renderer.pull` read the document id once, before its loop. When the active document changed while a display request for the earlier one was still waiting on a slow engine, `setDocument` could only queue a second pass; the loop then saw that the id no longer matched, stopped, and dropped the queued pass. Nothing was fetched for the new document and its pending fit never ran, until some later engine event started a pull. A failed request dropped a queued pass the same way.

The loop now reads the active document at the start of every pass and, when the document changed during a request, goes on to the queued pass for the new one. A failed request goes on when the document changed or a pass is queued and stops otherwise. No delay, no second fit and no extra request in the ordinary case; `setDocument`, `fitNow` and the per-document view are untouched, so a tab keeps the view the user left it with. The outer catch stays, so an error while applying a payload is swallowed as before.

Evidence: in headless Chrome with every engine request held for two seconds, a switch forced during a request in flight left the store empty before the change and showed the fitted plan after it. A plain click on a demo card did not hit the fault in that setup with requests held and the processor slowed 12 times.

OPEN, not fixed in 0.18.0: in the packaged Linux build of 0.17.0 and of 0.18.0, run on a virtual display with software rendering, a click on the 2D drafting card opens "Studio plan" with the grid and the axes only. The drawing appears on the first wheel step or zoom extents. What is known: the engine log shows one `GET /api/docs/<id>/display` answered 200 right after the open; the grid is already drawn at the fitted view (eight wheel steps back from the later picture give the same origin), so the store holds the drawing and the fit ran; moving the pointer, which repaints only the top layer, does not bring the drawing; a build with this entry's change and a build that also repainted all layers when the home closed (tried, then taken out) both still show it. Not reproduced in headless Chrome against the dev server, nor against the packaged engine's own interface with WebGL switched off. So the scene layer is not painted, or not presented, on the first frames after the data arrives in WebKitGTK there; whether a real Linux desktop or macOS shows it is not known. Next step: run the package with the web inspector on (`WEBKIT_INSPECTOR_SERVER`) and read `Renderer.runFrame`, `Store.work` and the painter on the first frames.

## A23, v0.18.0 the family design-language audit (styles/tokens.css, styles/p14b.css, styles/u3.css, styles/properties.css, eleven 3D layer files)

The family audit (`audit_design_lang.py` of the formai design-language pack, run on `frontend/`) went from 17 FAIL and 71 WARN to 0 FAIL and 67 WARN.

The 17 failures were one block: `styles/p14b.css` opened with a `:root` rule declaring the ECAD colours (`--ec-wire`, `--ec-fcu`, `--ec-board` and the rest) as raw hex outside the token sheet. They are the app's own media colours, so they keep their values and their names and now sit in the canvas block of `styles/tokens.css`, where the audit accepts them; `p14b/view2d.ts` reads them from `html` as before. Two stray literals went with them: the layer colour swatch's fallback `#fff` in `u3.css` is `--canvas-paper`, and `properties.css` read `--accent-hover`, a name declared nowhere, with `--accent-color-hover` as its fallback; it reads `--accent-color-hover` directly.

The 67 warnings that remain are all of one kind and are not defects: custom properties a component sets on its own element from code to carry a number or a per-instance value into its rule (`--p` for a progress fraction, `--pct`, `--dt-cols`, `--p11-rows`, `--gx-colour` for a node's own colour, `--u2-wf`, `--rn-cube-top`, `--vp1` and the like). The audit sees them read in a sheet and not declared in the token sheet; they are not tokens and must not be declared there.

Eleven files outside the canvas folders read a token with `getPropertyValue` and handed the text to three.js or a 2D canvas: the simulation and toolpath layers (`p12`), the mold layer (`p15`), the analysis scene (`an1`), the PMI and form layers (`p10`), the joint and comment layers and the plot (`p11`), the flat-pattern layer (`sheet`) and the result layer (`p13`). They worked because those tokens are plain hex today and would have broken the day one became a `color-mix`. All go through `tokenHex`, `tokenCss` or `tokenHexCss` of `canvas/ink.ts` now, with the same token names, fallbacks and scope elements. The comment markup written into an exported SVG gets a hex string so the file stands alone. One behaviour note: `p13/result-layer.ts` used to leave its colour alone when a token was missing and now applies the fallback, which is the colour the material was built with.

The pack's parity inventory script (`parity_inventory.py`) could not be run: it stops with a regular-expression error in its own pattern table on Python 3.12 and 3.13.

## T22, v0.18.0 AMOLED Black and the oled flag (ui/themes.ts, index.html, styles/tokens.css)

A 29th profile, id `amoled`, label AMOLED Black: the true-black theme formtxt added in 0.33.0, with the same values. `--bg-primary`, `--bg-secondary`, `--bg-node` and `--canvas-bg` are `#000000`, so on an OLED screen those pixels are off and panels are told apart by `--border-color` `#262626` and `--border-light` `#3a3a3a` alone. `--bg-tertiary` stays `#141414` because fields, menus and selected rows use it as their only fill. Text is `#ededed`, `#a6a6a6` and `#858585` (17.9, 8.6 and 5.7 to 1 on black), off-white to limit halation. High Contrast is not this theme: its panels are `#0a0a0a` and `#161616` and its borders are bright.

The profile is in both tables that hold the profiles: `THEMES` in `ui/themes.ts` and the pre-paint `PROFILES` in `index.html`, so a reload paints black on the first frame; a theme in one table and not the other paints Studio Dark first and then switches. In formCAD a `PROFILES` row has eleven columns: the ten of `NAMES` (the tenth is `--grid-color`) and then `--bg-node`. The swatch grid and the Dark theme list in Preferences are built from `THEMES` and needed no change.

`oled: true` on a profile makes `applyTheme` and the pre-paint script put `data-oled` on `html`; `applyTheme` takes it off for every other theme. CSS hangs the true-black exceptions on the attribute, not on the theme id, so another OLED profile needs only the flag. One block in `styles/tokens.css`, `:root[data-oled]`, holds them all:
- `--bg-hover` and `--border-soft` go from white at 6% and 8% to 10% and 12%. Over black the old values gave 1.10 and 1.14 to 1 against the surface where Studio Dark gets 1.17 and 1.24 from the same tokens.
- `--surface-1` is `--bg-primary`. Its mix of the window colour and `--bg-tertiary` came out `#090909`, lit pixels across every panel body.
- `--line-0` is `--border-color`. It is the window colour mixed toward black, which on black is black, so every hairline between the tab strip, the rail, the dock and the canvas vanished.
- `--canvas-bg-model` is `#000000` and the grid alphas go from 7% and 16% to 10% and 22%. The model-space canvas is `#212830` for every dark theme and does not come from the profile.

Not done: the desktop window's own background before the page paints is the shell's fixed `10, 10, 10` (`src-tauri/src/main.rs`), and the splash is the same for every theme.

## C21, v0.18.0 drawing surfaces resolve tokens through one probe (canvas/ink.ts new, canvas/media.ts new, canvas/*, view3d/*, render/*, p14b/*, p12/layer-preview.ts and the 3D layers)

The console showed `THREE.Color: Unknown color color-mix(...)` on every document. `p12/layer-preview.ts` read `--lp-bridge` and `--lp-gap` (which are `--accent-ink` and `--accent-color-hover`, both `color-mix`) with `getPropertyValue` and handed the raw expression to three.js, which cannot parse it, so the colour silently became something else. The same raw read was in the ECAD 2D views (`--ec-bg`, `--ec-paper`, `--ec-grid` straight into `fillStyle`), the 3D tooltip ink, the analysis and board layers, and `view3d/kit.ts`, which read `--canvas-selection`, a token defined nowhere, so the 3D selection highlight was grey.

`canvas/ink.ts` is now the one place a token becomes a colour: a hidden probe span per scope, created once, gets `color: var(--token)`, the browser computes it, and `parseCss` reads the `rgb()` or `color(srgb ...)` result. Results are cached per scope and token and the cache is dropped on a theme change. `tokenRgba`, `tokenCss`, `tokenHex` (for `setHex`) and `tokenHexCss` are the ways in. `--canvas-selection` is now declared in `tokens.css` as `#4a8fff`, the blue both canvases already fell back to.

`onThemeChange(cb)` in the same file is the one theme signal: it listens to `nm:ui-settings-changed` in the capture phase (so the cache is cleared before anyone reads), to `formcad:prefs-changed`, and to a MutationObserver on the `html` and `body` attributes, and notifies only when that signature changed. Subscribers repaint in the same frame; before, the 2D canvas and the 3D viewport refreshed one animation frame late, the ECAD board layer never refreshed, and the ECAD 2D views had an observer that missed the body class. Nothing is rebuilt on a theme change: colours are re-read and surfaces marked dirty.

The 2D grid takes its colour from `--text-primary` and its alpha from `--canvas-grid` and `--canvas-grid-major`: pixel-identical in Studio Dark (major grid 47, 54, 61 before and after) and visible on true black. The layout sheet's surround is the background colour under AMOLED. The app's own drawing colours (grips, snap and tooltip notes, constraint marks, view-cube ink, lights, the default body, render materials, ECAD fallbacks) are one named table, `MEDIA` in `canvas/media.ts`; axis, ACI, copper, silk and material colours stay where they were. ACI 7 already flips against the background through the `contrast` uniform.

Left: `graph/ops.ts` group swatches read a raw property and keep only six-digit hex; those values are stored as group data, not drawn from the theme.

Verified in headless Chrome against a running engine: the drafting, part and graph demos in Studio Dark, AMOLED Black and Light; background pixels 33, 40, 48, then exactly 0, 0, 0, then 223, 227, 232 on all three; the first animation frame after a live switch already in the new colours, also under 4x CPU throttling. Not verified: the render preview's live look, and the ECAD views on screen (their resolved values were read in the page).

## S20, v0.18.0 grouped tools on the rail (ui/tool-rail.ts new, ui/draw-rail.ts, styles/shell.css)

The group of the running command is lit with the existing active style; the sheet-metal tools report no running command and never light.

Zero flash: each button holds every icon of its group, built once, and a face change toggles `hidden`; each flyout is built once in `#overlay-root`, fixed, glass, in the menu z band, so opening one moves nothing. The rail is the same in every workspace because nothing in the code varies it; per-workspace sets would be a separate decision. It fits a 757 px page without scrolling (content about 594 px).

## S17, v0.17.0 splash and startup against formvis 2.3.5 (public/splash.html, src-tauri/src/main.rs, src-tauri/src/window_state.rs, backend/formcad_engine.py)

The shell was compared step by step with formvis 2.3.5. Already equal: the reveal module (`reveal.rs` is the same code), the hidden transparent 360 by 200 splash, the engine port handshake, the queue for `.fcad` and `.dxf` files that arrive before the page is ready, the exit gate (`exit-requested`, `confirm_exit`) and the engine stop (SIGTERM, 1.5 s, then kill). The page registers its exit listener before it marks itself ready, so a quit never waits on a page that is not listening.

Brought over. The splash bar carries the family's four-stop gradient (`#3A7BFF`, `#9A5CFF`, `#FF4F7A`, `#FFAE2B`) in place of the two-stop one; formCAD's icon and name stay. A web view that dies is reloaded once; a second death within two minutes replaces it with a plain page offering Restart FormCAD or Quit (`window_state::on_renderer_stopped`, `crash_loop`, `shell_choice`). Its links use the shell's own `formcad-shell` scheme, caught by the main window's `on_navigation` hook and never loaded; `renderer_choice` opens the exit gate, then restarts (stopping the engine first) or exits. Once that page is up the close button exits at once, since a dead page cannot answer a quit request. The shell passes its process id as `FORMCAD_SHELL_PID` and `watch_parent` in `formcad_engine.py` watches that id (POSIX only, as before), so the server exits when the shell is gone even if the frozen launcher was force-killed.

Not wired on Linux: formvis watches the renderer there through WebKitGTK's `web-process-terminated`, which needs `webkit2gtk` as a direct dependency. formCAD does not have it and none was added; the recovery page is macOS only (Tauri's `on_web_content_process_terminate`). Windows has no such hook in formvis either.

Left out, because they are not startup or formCAD has nothing behind them: the updater, the native renderer, display profile and desktop-integration modules, agent and MCP launch modes, launch runs (`--command`, `--action`, `--script`), fonts, `--no-skin` and interface zoom. formvis also chains every open onto one promise so live opens and waiting files never interleave; formCAD still starts one loop per batch.

Verified: `cargo check --release` and a full `tauri build` on Linux; `npx tsc --noEmit -p .`. The macOS-only code is not compiled on Linux, and the reveal and the recovery page have not been run on a desktop.

Documents carry `dirty` (boolean) beside `modified` (timestamp); closing and the tab dot read `dirty`. Workspace state is a `data-workspace` attribute on `.cv-app` instead of an event. Events with no listener (`tool-sets`, `hide-palettes`, `palette:layers`) were removed; `formcad:cursor` keeps its status bar listener for the canvas to come. Open and Save As use the Tauri dialog plugin (2.8.4, matching the Rust plugin) with `.fcad` and `.dxf` filters in the desktop app and a typed path in the browser; pending OS opens are drained at start and `formcad://open-paths` is followed. `@tauri-apps/api` is 2.12.4 because `tauri build` refuses a JavaScript API older than the locked Rust crate. Seventeen preference fields that duplicated engine variables were removed with the snap-mode table.

Flash fixes found under 4x throttling: the command-line keyword buttons were created and removed on every prompt; they are now a fixed pool of 16 slots patched in place. The centre title overlapped the 18 menu titles below 2300 px; it now shows only when native menus take the menu row or the window is wide enough.

Verified (Chromium 1440 by 900, CPU 4x, 150 ms latency, 1.6 Mbit/s, cache off): layout shift 0 after ready and after a LINE sequence; `#app` hidden in every frame before ready (0 of 376 and 0 of 388); 3 s idle, 0 node, text or attribute changes in status bar, title bar, command line, tabs and dock; during LINE no element added or removed in those containers except the history strip's rolling rows; zero console errors and zero failed requests.

## Family shell, preferences, command line and dock · _v0.2.0 (index.html, vite.config.ts, src/app.ts, src/main.ts, src/ui/, src/io/, src/styles/)

`app.ts` is the composition root: `mountShell()` builds the shell template once and returns every host element; `onShellMounted` and `onCapabilities` let sections register without editing `startApp`. `shell-part1.ts` registers the title bar, menus, tabs, Home and status bar; `shell-part2.ts` registers Preferences, the palette, the command line and the dock; each is one import in `main.ts`. `onCapabilities` registers at module load so the status bar never shows "Engine offline" before the first answer.

Menu items that are engine commands run `POST /api/docs/{id}/command` and show the engine's answer; nothing in the menus is a dead item. Drafting toggles in the status bar read and write system variables (AUTOSNAP bits 8 and 16 for polar and tracking, OSMODE bit 16384 for running snaps) and follow `sysvar` events; engine variables are the source of truth for drafting options, so the preference store keeps only interface settings. Edit shortcuts are left to a focused text field. The command palette key reads `Shift+Mod+P` because `comboOf` orders modifiers Alt, Shift, Mod.

The dev server injects the token meta by reading the engine's token file and stamps the header on proxied requests; the built interface gets the meta from the engine. Font preloads point at the dev paths and fall back to the CSS imports in the build.

Removed from the formvis carry-over: user skins, favourite themes, the dock-boot script and the remembered-values history; they belong to the image editor.

Verified: typecheck and build pass for each part; the built interface mounts in headless Chrome with no console errors.
